# Un-assessed learning-path signpost — browser verification

**Date:** 2026-08-04
**Branch:** `feature/unassessed-path-signpost` (commits `437a43d`, `eee1e2f`, `da0e928`, fix `5d65b83`)
**Verdict: PASS** on all four settled-state scenarios, plus a load-window scenario
added afterwards.

> **This first pass missed a regression, and the miss is instructive.** Every
> scenario below waited for `networkidle` and then for the tracks to render, so
> only the *settled* DOM was ever inspected. The final whole-branch review found
> that `levelCode` initialises to `null` while the page header renders before the
> graph arrives — so on first paint `notAssessed` was true for **every** learner,
> and an assessed learner briefly read "Take it first. It takes about 10 minutes."
> about an assessment they had already completed: the same class of wrongness this
> branch exists to remove. Fixed in `5d65b83` by gating the flag on `loaded`, and
> now covered by scenario 6, which deliberately delays the graph. The settled
> results below were re-confirmed unchanged after the fix.

## Method, and why it differs from the plan

The plan's Task 4 originally proposed reproducing the bug with "a test account with
no `survey_responses` row". That was not safe to do: **dev and prod are the same
Azure DB** (`ai-enablement-hub`), so creating or stripping survey rows edits live
learner data. A local backend was also ruled out — its lifespan task runs an
auth-cleanup `DELETE` against that shared database on startup.

What ran instead, writing nothing:

1. **Fixtures generated by the real backend service, read-only.** A script built an
   `AsyncSession` against the live DB and called the actual
   `LearningService.graph(user_id, effective_level)` for the reported learner
   (`axl.tanghe@delaware.pro`), once with `effective_level=None` (his true state) and
   once with `'explore'` (the assessed baseline). Only SELECTs ran. This makes the
   payloads production-exact rather than hand-authored, and it independently
   reproduced the bug at the service layer:

   | fixture | `maturity_level` | maturity-locked assigned tracks |
   |---|---|---|
   | `graph-unassessed.json` | `null` | **8** — General I, General II, Copilot, Claude, Obsidian, General III, Copilot II, Claude II |
   | `graph-assessed.json` | `'explore'` | 7 — **General I is unlocked** |

   That single row difference is the whole bug: General I is gated purely on the
   learner having a level at all.

2. **The frontend dev server alone**, with `window.fetch` patched in an init script
   to serve `/api/me`, `/api/me/journey` and `/api/learning/graph` from those
   fixtures. Any other `/api/*` path returned a loud `STUB_MISS` 500 so nothing could
   silently reach a real backend. **`stubMisses` was empty in every run.**

3. **Assertions on rendered text and computed styles**, not only on screenshots —
   `getComputedStyle` values are quoted below, so the verdict does not rest on
   reading a picture.

**Artifacts are deliberately not committed.** The drivers, fixtures and three
full-page screenshots lived in the git-ignored SDD workspace and were removed with
it. The durable evidence is the value tables below: every string and every
`getComputedStyle` result quoted here was read off the running page. If the
screenshots are wanted for a PR, they can be regenerated by re-running the drivers
against a fresh fixture dump.

## Scenario 6 — the load window (added after the final review)

`/api/learning/graph` delayed 2s, page opened with `waitUntil: 'commit'` so the
subtitle is read while the graph is still in flight. **PASS**, both directions.

| Learner | During load | Settled | Verdict |
|---|---|---|---|
| assessed | assessed copy | assessed copy | PASS — correct throughout |
| un-assessed | assessed copy (neutral) | un-assessed copy | PASS — nothing claimed before the level is known |

`tracksRenderedDuringLoad: false` in both runs confirms the mid-flight read really
happened before the track list appeared. Pre-fix, the assessed run would have read
the un-assessed copy here.

The fix is `notAssessed = loaded && resolvedLevelIdx === -1`. Gating on `loaded`
restores the header's pre-branch behaviour; keying on the resolved index rather
than `levelCode === null` also closes a latent path where a `maturity_level`
outside `LEVELS` would clamp to Explorer(0) and resurface the original bug.
`levelIdx` itself is numerically unchanged, so the access rule it feeds
(`rank < levelIdx` in `isUnlocked`) is untouched.

## Scenario 5 — the operational fix

Not run as a browser scenario, because it is scenario 1 by another name: pinning
`maturity_override` in the admin panel makes `MaturityService.effective_level`
return that level ahead of any survey, which is exactly the `graph-assessed.json`
payload already verified. Confirmed at the data layer instead — the same learner
yields `maturity_level: 'explore'` and an unlocked General I once a level resolves.

## Observations, and what stayed unfixed

1. **The CTA can land on a broken page.** `navigate('/assessment')` is
   unconditional, but `/api/survey/me` is hard-gated by
   `require_component_unlocked(component="assessment")`. A project with `learning`
   unlocked and `assessment` locked or hidden would send the learner to
   Assessment's "Failed to load your assessment progress" state. Narrow — the
   component defaults unlocked, and an admin who pins a level instead makes
   `notAssessed` false — and still better than the pre-branch dead end. **Left
   unfixed:** guarding it needs the project's component state, which this page does
   not hold (only JourneyHome fetches `/api/me/journey`). Follow-up candidate.
   Related: the spec's boundary note that JourneyHome "already surfaces the
   assessment card as available for these users" holds only when that component is
   not locked or hidden.
2. **"Nine buttons match Take the assessment" — downgraded to a non-issue.** Each
   locked lane is a `<button>` whose accessible name contains its subtitle, so the
   phrase appears 9 times in a loose selector. But each name *begins with its track
   name* ("General I Take the assessment to unlock"), so the names are unique and
   this is a selector artifact, not an a11y defect; the CTA click test hit the real
   button because the panel precedes the track list in DOM order. What remains is a
   UX judgement: a locked lane whose copy reads as an instruction but only expands
   on click. Optional follow-up — route locked lanes to `/assessment` while
   un-assessed.
3. **The spec's adjacency claim was imprecise and has been corrected.** It justified
   dropping `Unlocks at {Level}` on the grounds that the group header sits "directly
   above each lane"; that is exact only for the first lane in a group, and Integrator
   renders 3 lanes here (6 tracks exist), Multiplier 3. The screenshots show the
   grouping is visually unambiguous, so the reasoning holds — the sentence now reads
   "above each run of lanes" (`5d65b83`).
4. **No automated test** pins any of this; the repo has no frontend test runner and
   browser verification was the chosen substitute. The four-way subtitle ternary is
   the piece most exposed to a silent regression if someone reorders its arms later,
   and `checkpointState` / `groupHeaderState` are pure functions over primitives —
   the obvious first tests if a runner is ever introduced.

## What this verification does NOT establish

Stated plainly, because a verification doc that only lists passes is not evidence.

- **"Pixel-identical to today" was never demonstrated by comparison.** No screenshot
  or DOM capture from a build of the base commit `91c1ac7` exists. What was
  established is that the post-change assessed rendering matches the expected
  strings and computed styles enumerated above, plus a character-for-character
  string comparison of the moved subtitle constant and a term-by-term trace of both
  extracted helpers against the code they replaced. The conclusion rests on that
  reasoning, not on an image diff.
- **Scenario 3 proved the route change only.** `/api/survey/me` was stubbed just
  enough for `/assessment` to mount; nothing establishes that the assessment page
  renders correctly for this learner class in production. See observation 1.
- **The un-assessed admin / `user+` case was not exercised visually.** It is out of
  scope per the spec, and the code path is clear (nothing is locked for them, so the
  lane branches never fire; the level card still reads "Not assessed yet", which is
  true), but it was not rendered.
- **Scenario 5 was reasoned, not run** — see that section.
- **Everything ran against stubbed API responses.** The payloads came from the real
  service, but no request crossed the network to a real backend, so nothing here
  exercises serialisation, auth, or the component gate end to end.
