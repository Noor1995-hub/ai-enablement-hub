# Introduction "level" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a mandatory pre-Explorer "Introduction" track/group that everyone must complete before any other track unlocks, rendered as its own level group with its own progress bar but absent from the maturity stepper, "% of full path", CURRENT LEVEL card, and assessment graphic.

**Architecture:** Introduction is NOT a maturity level. It is (a) a distinguished track flagged by a new `tracks.is_introduction` boolean, implicitly assigned to and always unlocked for every learner (correct-by-construction "obligatory for everyone"), and (b) a client-side completion gate that adds `&& introductionComplete` to the unlock rule of every *other* track. Because Introduction stays out of the `LEVELS`/`LEVEL_ORDER` constants, every level-index UI element keeps working untouched.

**Tech Stack:** FastAPI (Python 3.13, uv, SQLAlchemy async, Alembic) + React 18 + TypeScript (Vite) + Azure PostgreSQL. Backend tests: pytest against the `ai-enablement-hub-test` PG DB. Frontend checks: tsc + ESLint + Vite build (no frontend unit-test runner).

## Global Constraints

- Backend checks after changes (run inside `backend/`): `uv run poe format && uv run poe lint && uv run poe test`.
- Frontend checks after changes (run inside `frontend/`): `npm run typecheck && npm run lint && npm run build`.
- New Alembic migration's `down_revision` MUST be `"d8e9f0a1b2c3"` (the current head — verify with `uv run alembic heads`).
- The Introduction track's exact literals: name `Introduction`, tagline `Let's get familiar`, color `#941914`, `track_type='general'`, `required_level='explore'`, `sort_order=0`.
- Introduction MUST NOT be added to `backend/src/core/constants.py` `LEVEL_ORDER` nor `frontend/src/lib/levels.ts` `LEVELS`. Do NOT touch the OVERALL JOURNEY stepper, `overallPct`/`levelFraction`/`levelIdx`, the CURRENT LEVEL card, `LEVEL_GRADIENT`, or `Assessment.tsx`. No CHECK constraint changes.
- Locks (incl. this gate) are visibility filters, NOT access control — do not add server-side access checks to learning endpoints; the gate is computed on the client.
- The integration-test DB schema is built from `Base.metadata` (not migrations), so every model column change is visible to tests immediately; the Alembic migration is exercised separately by a migration-sanity test.
- `frontend/src/api/schema.d.ts` is committed and generated by `npm run gen:api` with the backend running. Regenerating it starts the dev backend, whose lifespan runs a one-time auth-cleanup `DELETE` against the real Azure dev DB — this side effect is expected (user has approved it before); flag it when you run the step.
